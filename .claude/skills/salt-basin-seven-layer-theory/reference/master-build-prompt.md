SALT BASIN NET WORKS

Seven-Layer Theory, Matrix & Journey Engine

Claude Code Implementation Specification — Version 0.1

Implementation type: Extension of existing platform
Database: Existing Supabase project
Frontend: Existing Salt Basin application
Visualization: Existing process-flow and diagram builder
Primary requirement: Preserve and extend existing functionality.

⸻

1. PRIMARY OBJECTIVE

Extend the existing Salt Basin platform to support a unified mathematical, musical, scientific, business, computational, visual, and Rest-based modeling framework.

The system must enable users to:

1. Define and manage seven foundational architectural layers.
2. Maintain seven definitions for every registered concept.
3. Create multidimensional matrices with three-dimensional visual projections.
4. Model entities and their relationships using graph and hypergraph structures.
5. Compose independently identifiable data elements into Journey Data Rods.
6. Configure up to 12 intervals within a defined temporal cycle.
7. Dynamically calculate progression, weights, eligibility, and dependencies.
8. Construct interconnected journeys using the existing diagram builder.
9. Link matrices, process flows, diagrams, Journey Rods, Staffs, and Sheets.
10. Persist definitions, configurations, relationships, and changes in Supabase.
11. Preserve source lineage, version history, and decision status.
12. Reuse existing Salt Basin product definitions and calculation engines wherever applicable.

Do not create a separate application, disconnected modeling environment, or independent database.

⸻

3. SEVEN FOUNDATIONAL ARCHITECTURAL LAYERS

Create or extend a registry supporting these seven layers.

ID	Layer	Mathematical foundation	Music theory	Scientific foundation
L1	Identity	Set theory, identity relations	Notes and pitch identity	Classification and measurement identity
L2	Relationships	Graphs, hypergraphs	Intervals and contextual relationships	Network science
L3	Composition	Set composition, incidence structures	Chords, harmony, voicing	Compositional systems
L4	Time	Interval algebra, temporal systems	Rhythm, meter, tempo	Dynamical systems
L5	Business Logic	Predicate logic, state machines	Harmonic and voice-leading constraints	Formal verification
L6	Measurement	Linear algebra, statistics	Frequency ratios and rhythmic proportions	Metrology and uncertainty
L7	Visual Representation & UX	Geometry, graph layout	Musical notation and score layout	Cognitive science and information visualization

Each layer must have a stable identifier.

Layer definitions must be versioned.

Do not hardcode business-specific interpretations into the universal layer definitions.

4. SEVEN REQUIRED DEFINITIONS

Every registered concept must support seven definition perspectives.

ID	Definition
D1	Mathematical
D2	Musical
D3	Scientific
D4	Business
D5	Computational
D6	Visual
D7	Rest

The seventh definition is always Rest.

Rest must be independently defined for every concept.

Definition record requirements

Each definition should support:

* Concept identifier
* Definition type
* Definition text
* Formal expression, where applicable
* Source or reference
* Equivalence classification
* Validation method
* Version
* Approval status
* Effective date
* Superseded date
* Author
* Last modified timestamp

Equivalence classifications

Support:

* Literal equivalence
* Structural correspondence
* Design analogy

Do not describe a business analogy as a scientifically proven equivalence.

Definitions may initially be incomplete.

Represent incomplete definitions explicitly rather than generating unsupported claims.

6. HYPERGRAPH RELATIONSHIP ENGINE

Support canonical entities and independently identifiable relationships.

The system must represent:

* Bilateral relationships
* Multi-party relationships
* Directed relationships
* Undirected relationships
* Typed participation roles
* Relationships between relationships
* Nested compositions
* Temporal relationship states

Use a mathematical model equivalent to:

[
H=(V,\mathcal{E})
]

Where:

* (V) represents canonical entities.
* (\mathcal{E}) represents relationships involving one or more entities.

Critical identity rules

An entity must retain its canonical identity regardless of:

* Its position in a diagram.
* Its participation in a relationship.
* Its contextual clef assignment.
* Its membership in a fund or portfolio.
* Its participation in multiple journeys.

Contractual composition

Support separately identifiable:

1. Legal entities.
2. Contracts.
3. Contractual relationships.
4. Multi-party arrangements.
5. Higher-order compositions.

Do not automatically infer a master contract from the existence of three bilateral contracts.

Do not equate a reporting composition with a legally executed agreement.

Provenance

Every derived relationship must reference the source relationships, governing rule, and effective time used to establish it.

7. MUSICAL COMPOSITION ENGINE

Preserve the following established Salt Basin concepts.

Note

An independently identifiable data component.

Chord

A composition of participating notes.

Journey Data Rod

A persistent composition identity whose participating notes may change over time.

Clef

A contextual interpretation of a party’s position within a bilateral relationship.

Universal C

The canonical relationship definition connecting the contextual parties.

Staff

A complete journey cycle.

Journey Sheet

A coordinated collection of one or more Staffs.

Measure

A shared temporal alignment unit.

Beat

A subdivision within a measure.

Rest

An explicitly governed nonparticipation state.

Musical sections

Business stages that may overlap or cross measure boundaries.

Do not assume a change in chord membership creates a new Rod identity.

Do not assume that a business-defined clef has exactly the same semantics as a conventional musical clef.

⸻

8. TWELVE-INTERVAL TEMPORAL ENGINE

Support configurable cycles containing between 1 and 12 intervals.

Each interval must support:

* Sequence
* Start
* End
* Duration
* Relative position
* Business classification
* Applicable rules
* Associated measures
* Applicable requirements

Intervals may have unequal durations.

Support distinct:

* Calendar time
* Effective time
* Recorded time
* Progression time
* Expected completion time

Do not assume equal-tempered musical frequency ratios imply equal business durations or weights.

Allow different Staffs to use different temporal configurations while retaining the ability to align them on a common timeline.

9. BUSINESS LOGIC AND CALCULATION ENGINE

Reuse the existing calculation infrastructure wherever possible.

Support:

* Rule applicability
* Eligibility
* Dependencies
* Stage gates
* Thresholds
* Authorized rests
* Required participation
* Completion validation
* Dynamic weights
* Expected progression
* Actual progression
* Variance calculations

Calculation requirements

Every calculated result must retain:

* Input references
* Applicable rule versions
* Calculation method
* Temporal context
* Output value
* Validation status
* Calculation timestamp

Weights must be normalized only across eligible requirements.

Do not treat missing data as an authorized Rest.

Do not automatically treat the removal of requirements as improved performance.

Do not aggregate incompatible financial measurements.

⸻

10. REST ENGINE

The Rest is the seventh required definition.

Support at least these participation states:

* Active
* Sustained
* Authorized Rest
* Pending
* Failed
* Unknown

An authorized Rest must include:

* Governing rule
* Applicable context
* Effective interval
* Reason
* Approval or authorization reference, when required
* Calculation implications

The system must distinguish nonparticipation from missing evidence.

11. INTEGRATION WITH EXISTING PROCESS-FLOW AND DIAGRAM BUILDER

This is a primary implementation requirement.

Do not build a replacement diagram editor.

Extend the existing builder to support the new matrix and journey structures.

Required capabilities

Users should be able to:

* Create a matrix from the existing builder.
* Select its three visible axes.
* Change axis dimensions.
* Add or remove participating entities.
* Connect matrices to process-flow nodes.
* Connect Journey Rods to matrix intersections.
* Navigate between related matrices.
* View relationships across multiple journeys.
* Expand or collapse compositions.
* Inspect the seven definitions for any concept.
* Inspect applicable Rest definitions.
* View effective-time changes.
* Preview calculated effects before committing changes.

Bidirectional interaction

Visual edits must generate proposed changes to the underlying model.

They must not silently mutate canonical identities or contractual relationships.

Changes should pass through:

1. Validation
2. Business-rule evaluation
3. Dependency analysis
4. Calculation impact analysis
5. Authorization, where applicable
6. Persistence
7. Audit logging

The existing diagram builder should remain the primary authoring interface.

12. SUPABASE PERSISTENCE

Use the existing Supabase project.

Inspect the schema before proposing migrations.

Prefer reusable registries and relationship tables over a separate table for every matrix.

Potential logical entities include:

* Theory layers
* Definition types
* Concepts
* Concept definitions
* Matrix definitions
* Matrix dimensions
* Matrix projections
* Matrix values
* Canonical entities
* Relationships
* Relationship participants
* Compositions
* Composition members
* Temporal intervals
* Business rules
* Calculation definitions
* Calculation results
* Diagram bindings
* Journey bindings
* Definition versions
* Audit events

These are logical entities, not mandated physical table names.

Reuse existing tables where their semantics and constraints are compatible.

Database requirements

* Preserve existing records.
* Maintain referential integrity.
* Respect existing tenant isolation.
* Preserve Supabase Row Level Security.
* Use controlled migrations.
* Maintain immutable audit history where required.
* Support historical and effective-date queries.
* Avoid storing the same canonical entity multiple times.

Use transactions for changes that must be committed atomically.

13. PREPOPULATION

Seed the seven foundational layers.

Seed the seven definition types.

Seed the 49 proposed matrix families.

Populate established mathematical, musical, and scientific definitions using defensible sources.

Use existing Salt Basin definitions where they are available in the repository or approved product documentation.

Do not invent Salt Basin product definitions.

Unconfirmed mappings should remain explicitly marked as proposed.

Required definition statuses

* Published baseline
* User-confirmed
* Proposed
* Inferred — needs confirmation
* Conflict
* Deprecated

Preserve the original source and prior value when a definition changes.

14. PRODUCT-SPECIFIC DEFINITION WORKFLOW

Users must be able to select:

Product → Architectural Layer → Matrix → Concept → Seven Definitions

The system should display the prepopulated theoretical definitions alongside editable Salt Basin-specific definitions.

For example:

Product: HOS
Layer: Composition
Matrix: Journey Data Rod
Concept: Chord

The user should be able to inspect the mathematical, musical, and scientific foundations and then define the business, computational, visual, and Rest behavior for that product.

Support drafts and approval workflows.

Do not overwrite the universal theoretical definition when a product-specific definition is edited.

16. IMPLEMENTATION SEQUENCE

Proceed incrementally.

Phase 1 — Discovery

Inspect the application, Supabase schema, existing builder, and calculation engines.

Phase 2 — Architecture

Produce a proposed extension design and identify reusable components.

Phase 3 — Persistence

Create approved schema extensions, migrations, and registry seeds.

Phase 4 — Theory Registry

Implement the seven layers and seven definitions.

Phase 5 — Matrix and Hypergraph Engine

Implement configurable matrices, relationships, and composition.

Phase 6 — Temporal and Calculation Engine

Implement interval configuration, progression, weights, and Rest evaluation.

Phase 7 — Existing Builder Integration

Extend the process-flow and diagram builder with matrix and journey authoring.

Phase 8 — Validation

Execute integration, mathematical, persistence, and regression tests.

Do not advance automatically from discovery to implementation without presenting the compatibility assessment and proposed architecture for review.

⸻

17. DEFINITION OF DONE

The implementation is complete when:

* All seven architectural layers are registered.
* All seven definition perspectives are supported.
* The seventh definition is consistently Rest.
* The 49 initial matrix families are available.
* Matrices can be configured without new database tables.
* Multi-party and relationship-level compositions are supported.
* Journey Rods retain their identities as composition changes.
* Temporal configurations support up to 12 intervals.
* Business logic and calculation results are reproducible.
* The existing diagram builder can create and link matrices and journeys.
* Definitions and relationships persist in the existing Supabase database.
* Historical changes remain auditable.
* Existing Salt Basin functionality continues to operate.
* Users can progressively define Salt Basin product-specific interpretations without modifying universal theory definitions.

Primary engineering principle: Extend the existing platform and preserve its source of truth.
