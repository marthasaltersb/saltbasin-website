Static definition of each phase's scope. Do not edit this file to record progress — progress, findings,
and status live in `docs/salt-basin-world-variants-progress.md`, which is the mutable state the skill reads
and updates on every run.

Source spec: `master-build-prompt.md` (verbatim, roman-numeral sections I–XIX plus the framing preamble,
supplied 2026-07-12).

## Rules that apply across every phase (do not repeat inline, just obey them)

- **The visual world may change; the semantic meaning must never change.** Every metric value (Query
  Relevance, Coverage, Confidence, Stability, Position, Completeness, Readiness, Maturity, Density,
  Coherence, Alignment) must be computed exactly once per query/selection and handed to whichever variant
  is active — never recomputed per variant, never redefined by a variant.
- **No `if variant === "x"` scattered through render components.** Resolve a structured `WorldVariantConfig`
  once, then feed the same generic render systems (Orbit/Atom/Molecule/Rod/Lineage builders) the resolved
  profile. If you find yourself writing a variant conditional inside an unrelated component, stop — that
  conditional belongs in the profile resolution layer instead.
- **One primary visual channel = one semantic metric, within a single variant.** Mapping both confidence
  and temporal freshness onto the same opacity channel in the same variant is the exact conflict §IV
  prohibits — Phase 3's validation rules must catch this, not just describe it.
- **Never invent a new path color per world.** `pathColor.js`'s `resolvePathColor()`/`PINNED_PATH_COLORS`
  (revenue=gold, customer=teal, member=mauve, deterministic hash fallback for everything else) is the real,
  already-shipped implementation of §XII's permanent-path-color rule. Every variant reuses it unchanged.
- **Never let user-level customization redefine semantic directionality.** "Make higher Query Relevance
  mean farther away" is explicitly prohibited (§X) — the permitted personalization surface (camera
  sensitivity, environmental density, label scale, motion, variant choice, grid visibility) never includes
  which direction a metric's value moves a visual property.
- **Preserve, don't rebuild, the already-correct rendering/semantic separation.** `computeAtomVisual()`
  (`maturity.js`) already does maturity (semantic) → scaleY/facet/opacity/metalness/roughness (rendering)
  correctly, never the reverse — this is the template for every new profile's metric→channel mapping, not
  something to redesign from zero.
- **"Orbit" is canonical — resolved 2026-07-12.** The spec text originally read "Orbin"; Betsy confirmed
  this was shorthand/typo for "Orbit," matching the already-shipped term. Same resolution recorded in
  `salt-basin-visual-metrics`, which shared this decision.
- **Flag naming collisions, don't paper over them.** `src/config/visual/worldRegistry.js`'s existing
  `WORLD_REGISTRY`/`getWorldDefinition`/`worldId` is a **content-domain** switcher (Foundation / Channel Rod
  / Query Channel / Career / Pricing / Infrastructure / Templates — different data per entry) and is
  distinct from this spec's `WorldVariant` (same data, different spatial metaphor). Phase 1 records this as
  an open naming decision — carry it forward, don't collapse the two concepts into one registry by fiat.
