and status live in `docs/salt-basin-website-intelligence-progress.md`, which is the mutable state the skill
reads and updates on every run.

## Rules that apply across every phase (do not repeat inline, just obey them)

- **The system is not a copywriter, template picker, or HTML generator.** Every phase's output must be
  structural (a model, registry, engine, or configuration change) — a strategy document or findings list
  alone never satisfies a phase.
- **Configuration-driven, never hardcoded.** Generated pages/sections must resolve through
  `src/components/blocks/index.jsx`'s `REGISTRY` and existing `site_state`/`member_sites` shapes. Never emit
  organization-specific content baked into a generic component's implementation.
- **Draft/published + append-only registry invariants from `CLAUDE.md` are absolute.** No phase writes
  directly to a published row; no phase renames or removes an existing `REGISTRY` key or `section.type`.
- **Never fabricate evidence.** Customer counts, revenue, metrics, partnerships, case studies, adoption,
  patents, certifications — none may be invented. Claims without evidence get ASPIRATIONAL/VISION framing
  ("designed to support"), never FACTUAL framing ("currently supports").
- **Preserve Betsy's actual voice and the Foundation Source of Truth.** Do not rewrite a distinctive phrase
  to sound more generic, and do not contradict `docs/salt-basin-foundation-source-of-truth.md`'s canonical
  entity/product names — reconcile into it, never around it.
- **Run `salt-basin-config-audit` on any new weighted formula or scoring model** (relevance/coverage/
  confidence-style calculations in Phase 6, metric composites in Phase 10) before considering that phase
  done.
- **No opaque composite scores.** Every metric this skill introduces must answer one named question, per
  §XXI — same rule `salt-basin-visual-metrics` already enforces for its own metrics.
