# Salt Basin Master Build

This skill drives Betsy's "Ultimate Master Build Prompt" — a ~97-section architectural brief for turning the Salt Basin site into a spatial, agentic, semantic operating environment (not a website with 3D bolted on). The full verbatim brief is too large to act on in one shot and is explicitly designed as 20 repeatable reconciliation loops (its own §96) — that's the shape this skill preserves. Each invocation advances the build by one loop (or a specific loop the user names), not the whole thing at once.

## Non-negotiables (apply on every invocation, no exceptions)

- Never rename `BestyStaff` — the spelling is intentional.
- Never reintroduce the retired five-pillar Salter Momentum model. Canonical: **UNDERSTANDING → RENDERING → MANIFESTING**.
- Never silently rename or reinterpret an intentional Betsy-defined term. Flag conflicts; don't resolve them by fiat.
- Config describes intent, code provides capabilities — routine semantic/visual changes should not require a React rewrite once the config layer exists (master prompt §47).
- A loop is not "done" permanently — it's meant to be re-run as the codebase and Betsy's direction evolve.
- Every loop runs the `salt-basin-config-audit` skill (`/config-audit`) before and after its structural work — see step 4. No loop ships a hardcoded product assumption without it being classified.
- Loops 2, 3, 6, 7, and 16 depend on the Member/Organization identity, access, and personal-config layer defined in `reference/member-org-admin-config.md`. That layer is built by the `salt-basin-pre-build` skill, not by this skill directly — see step 2b. Don't reconcile-and-stop against that spec as a document; invoke pre-build so the loop validates against real schema.
- No loop is marked `done` in the progress tracker without running the `salt-basin-regression-gate` skill (`/regression-gate`) against its scope first — see step 5. A loop that renders but hasn't been driven as an interacting user, checked for Channel/Agent-authority regressions, and reconciled against the Foundation is not complete; it's `pending regression gate`.
- Loops 9 (Visual Language) and 11 (Query Convergence) are not `done` merely because their rendering/convergence *mechanism* exists — a displayed score, percentage, or convergence behavior with no defined business or semantic meaning (or one that conflates convergence with maturity, coverage, or confidence) fails these loops even if it renders without error. Both depend on the `salt-basin-visual-metrics` skill (`/visual-metrics`) — see step 2c.
- Loops 9 (Visual Language) and 10 (World Navigation) are not `done` if the 3D environment can only render one spatial metaphor for its data, or if selection handlers call scene-mutation/positioning functions directly instead of dispatching a semantic Interaction Intent. Both depend on the `salt-basin-world-variants` skill (`/world-variants`) — see step 2d. That skill's own metric inputs come from `salt-basin-visual-metrics` (step 2c) — don't invoke world-variants ahead of the metrics it needs to render.

It doesn't build new spatial features — it audits and redesigns the *mathematical meaning* of values Loop 9 (Visual Language) and Loop 11 (Query Convergence) render, separating rendering math from semantic/business math and giving every displayed number a defined business question it answers. Loops 9 and 11 depend on it — see step 2c below.
- `.claude/skills/salt-basin-world-variants/SKILL.md` — a sibling driver (its own 9-phase driver, `docs/salt-basin-world-variants-progress.md`) for the "Master Build Prompt — Salt Basin 3D World Variant Engine." Loops 9 and 10 depend on it — see step 2d below. Its Phase 1 audit already found the current convergence code (`SpatialJourneyWorld.jsx`'s `runCustomerOrbit`/`runStageQuery`) computes positions inline with no Interaction Intent dispatch layer — the literal anti-pattern its source spec's §XV warns against.

## Workflow for every invocation

1. Read `docs/salt-basin-master-build-progress.md` first. Check the "Flagged conflicts" section — resolve or explicitly re-flag any that block the loop you're about to run.
2. Determine which loop to run:
   - If the user named one (`/salt-basin-build loop 6`, `/salt-basin-build agents`), run that loop.
   - Otherwise, pick the first loop in `reference/loops.md` whose status is `not started` or `blocked` (with its blocker now resolved).
2b. If this loop's row in `reference/loops.md` notes it's "built via `/salt-basin-pre-build` phase N" (currently loops 2, 3, 6, 7, 16), read `docs/salt-basin-pre-build-progress.md` for that phase's status:
   - If `not started` or newly-unblocked, invoke the `salt-basin-pre-build` skill for that phase now, before continuing this loop's own work — this loop should validate/extend against real schema, not reconcile against a spec that's still just a document.
   - If `blocked` (an open decision, or a genuine cross-spec dependency like Phase 3's unbuilt Career Atom/Molecule model), don't force it. Note the block in this loop's changelog entry and proceed with only the portion of this loop's own scope that doesn't depend on the blocked phase.
   - If already `done`, just proceed — read the pre-build phase's changelog entry for what's now real before continuing.
2c. If this loop is 9 (Visual Language) or 11 (Query Convergence), read `docs/salt-basin-visual-metrics-progress.md` for its phase statuses:
   - If the phase(s) this loop's scope needs are `not started` or newly-unblocked, invoke the `salt-basin-visual-metrics` skill for the relevant phase now, before continuing this loop's own work — the loop's "done" bar is the metrics skill's semantic-meaning bar, not just mechanism existing.
   - If `blocked` on an open decision, don't force it. Note the block in this loop's changelog entry and proceed with only the portion of this loop's own scope that doesn't depend on the blocked phase. (The prior "Orbin" vs. "Orbit" terminology question is resolved — "Orbit" is canonical, per Betsy 2026-07-12.)
   - If already `done` for the relevant phase, proceed — read that phase's changelog entry for what's now real before continuing.
2d. If this loop is 9 (Visual Language) or 10 (World Navigation), read `docs/salt-basin-world-variants-progress.md` for its phase statuses:
   - If the phase(s) this loop's scope needs are `not started` or newly-unblocked, invoke the `salt-basin-world-variants` skill for the relevant phase now, before continuing this loop's own work.
   - If `blocked` (an open decision — e.g. the `WORLD_REGISTRY` naming collision — or a genuine dependency on `salt-basin-visual-metrics` metrics not yet landed), don't force it. Note the block in this loop's changelog entry and proceed with only the portion of this loop's own scope that doesn't depend on it.
   - If already `done` for the relevant phase, proceed — read that phase's changelog entry for what's now real before continuing.
3. Read only the master-prompt sections that loop's row in `reference/loops.md` cites — via Grep/Read on `reference/master-build-prompt.md`, not the whole document.
4. Do the actual reconciliation work per master-prompt §93's sequence for that loop's scope:
   a. Run the `salt-basin-config-audit` skill in **pre-implementation** mode against this loop's planned scope — catch hardcoded assumptions before writing code, and identify which existing config surfaces (from its surface table) this loop should route through.
   b. Inspect current code → inspect current data/schema → inspect Foundation Source of Truth (`docs/salt-basin-foundation-source-of-truth.md`) → identify conflicts/gaps → classify each gap as Foundation / schema / configuration / formula / seed data / scenario / agent rule / visual rule / simulation rule → make the structural correction in code/config, not just a written list (§96's closing instruction is explicit that a list alone is insufficient).
   c. Run `salt-basin-config-audit` again in **post-implementation** mode against the loop's actual diff. Convert any in-scope SHOULD BECOME CONFIGURATION findings now; carry the rest into step 6.
5. Run the `salt-basin-regression-gate` skill (`/regression-gate`), scoped to this loop's diff, before this loop can be marked `done`:
   - Work through every gate section — interaction testing as a real user, Channel creation rules, the full enterprise deal Channel, Agent authority/concurrency, cross-Rod query convergence and temporal lineage, and the architecture-regression checklist.
   - Treat its Foundation Source of Truth reconciliation as this loop's reconciliation — don't run a second, separate Foundation pass in step 6.
   - If the gate fails any section, do not mark the loop `done`. Set its status to `pending regression gate` (or keep it `in progress`), record the specific failed states in the changelog, and fix them before re-running the gate — a loop that renders but fails the gate is not complete.
6. Update `docs/salt-basin-master-build-progress.md`: set the loop's status (`done` only if the regression gate passed in full), add a changelog entry (date, what changed, what's still open, the gate's PASS/FAIL outcome), add/update any newly discovered conflicts to the flagged-conflicts section (including any the gate surfaced), and record any TEMPORARY PROTOTYPE DEBT the audit surfaced (never let it go unrecorded).
7. Report back concisely: which loop ran, what structurally changed, the regression gate's outcome (pass, or what specifically failed), what the config audit found (converted items + prototype debt), what's still open, and what loop is next.
8. Invoke the `salt-basin-contribution-intelligence` skill (`/contribution-intelligence`) to feed this loop's own session into it as real evidence — per that skill's §XXI, the system is built against real Claude session data, not synthetic metrics, and a master-build loop session is exactly that kind of real data. If that skill's Phase 1 (repo inspection + foundational schema) hasn't landed yet, this step is a no-op: say so in the report and don't force a premature ingestion pass. Once Phase 1+ exist, let it run its own next-unblocked-phase logic rather than dictating which phase from here.

## Scope discipline

This is a large brief spanning schema, security, 3D rendering, agents, and finance. Don't try to satisfy all 97 sections in one turn — that produces shallow, unverifiable changes across too much surface area. One loop per invocation (or one section if the user asks narrowly) keeps each change reviewable and keeps the progress tracker meaningful. If a loop's scope is still too large for one turn, say so and propose splitting it rather than doing a shallow pass.

## Known conflicts to resolve early (see progress tracker for full detail)

- **Journey vs. Channel terminology.** Master prompt §3 calls for a full rename; live code (`src/lib/journeyEngine/*`, `server/routes/journeyRods.js`, `src/data/journeyWorldConfig.js`) uses Journey as the real shipped vocabulary. Don't rename mechanically — this needs a Betsy decision per §1's own rule.
- **Overlapping semantic models.** Master prompt §5 defines a much larger Basin→Port→...→Channel Rod Staff model than the already-shipped 3-tier Atom/Joint/Molecule metadata model and the existing 9-layer EIDOS schema (`server/lib/eidos.js`). Reconcile before adding a fourth parallel model.
- **Member/Org authority-model granularity.** `reference/member-org-admin-config.md` proposes new `authorityProfileIds`/`moduleAccessProfileIds`/`viewAccessProfileIds` arrays that duplicate, at finer granularity, what the shipped `org_memberships.role` + `product_licenses.tier` + `data_entitlements.scope` already do — and what a separate pre-existing spec (Member Portal Crystal & Agentic Layer) already solved by deriving org-admin capability from `data_entitlements` alone. Unify before building either. Full detail: `docs/salt-basin-master-build-member-org-reconciliation.md`.
