## Phase 1 inspection findings (2026-07-13) — three pieces of prior art already exist

Before any new schema: this repo already contains **three separate, partially-overlapping implementations** of pieces of this exact spec. None of them is the Contribution Event / immutable-raw-store / lineage-graph model described in `reference/master-build-prompt.md`, but all three do real work and at least one (#1) drives numbers Betsy currently relies on. Phase 1 cannot responsibly add a fourth parallel model without reconciling these — see the open decisions below.

1. **Legacy "v0.17 Contribution Intelligence Methodology"** (`server/data/contributionMethodology.js`, `server/routes/methodologyStats.js`, `scripts/analyze-contribution-sessions.mjs`, `scripts/store-session-analysis.mjs`, `scripts/reconcile-backlog-hours-full.mjs`). Claude-only, backlog-item-centric, not event-level:
   - Real burst analysis of Claude Code `.jsonl` transcripts (idle-gap bursts, real-human-turn filtering that excludes tool-result echoes and context-compaction/task-notification synthetic messages) — this is a working, real (non-synthetic) implementation of §VII's Time Intelligence evidence model, just coarser-grained (per-session, not per-event) and Claude-only.
   - `hours_claude` / `hours_betsy` / `cost_usd_claude` / `traditional_cost_usd` columns live directly on `backlog_items` (server/db.js ~967-1053) — computed via `RATE_CONFIGS_2026` ($225/hr Betsy director rate, $115/hr Claude quality-adjusted rate, $175/hr onshore-senior benchmark). This is a working Cost Ledger + Traditional Build Comparator (§VIII/§IX), but at backlog-item granularity, not Contribution Event granularity, and it **overwrites** these columns on reconciliation passes (v0.18.1–v0.18.5) rather than versioning attribution (conflicts with §XX's never-silently-rewrite rule — though this system predates the new spec).
   - `methodologyStats.js`'s `/summary` route exposes `aiSavingsUsd` / `aiSavingsMultiple` — this is exactly the unqualified "AI saved X hours/dollars" framing §X says not to present as fact. Predates the new spec; not yet reconciled against it.
   - Self-documented `knownGaps` in `contributionMethodology.js` already disclose: the `sessions` table name collision with the auth-cookie `sessions` table (the v0.17 analytics `sessions` table CREATE was a silent no-op against the live auth table — analysis is actually persisted via `config_state.contribution_session_analysis` instead), weak Tier-2 evidence for 41 pre-2026-06 backlog items (source transcript lost), and an explicit unresolved gap for non-Claude AI tool work (item #111, built in Codex, "has no JSONL transcript and can't be measured by any tier of this methodology, which is Claude/Anthropic-specific").
   - Real numbers from this system are shown on `/output/methodology` (member-facing IP page) and presumably `/output/build-summary`.

2. **`.codex/contribution-intelligence/` — a live Codex-side raw event adapter**, already wired into `npm run build` via `postbuild` → `scripts/run-codex-contribution-intelligence.mjs` (also runnable directly via `npm run contribution:codex`). This is a real, working implementation of §XIX's "Raw Source Connector + Immutable Raw Event Store" for `sourcePlatform: CODEX`:
   - Reads Codex sandbox logs (`~/.codex/.sandbox/sandbox.*.log`), filters to lines mentioning this project, computes a deterministic SHA-256 `id` per `file:line:content` key, and idempotently appends only new ids to `.codex/contribution-intelligence/codex-observable-events.json` (schemaVersion 1; fields: id, sourcePlatform, sourceFile, sourceLine, sourceTimestamp, ingestedTimestamp, eventType [TEST_EXECUTION/ERROR/FILE_UPDATE/COMMAND_EXECUTION/TOOL_ACTIVITY], payloadHash, observableEvidence, evidenceType). As of 2026-07-13 it has processed 10 sandbox log files into 3,086 deduplicated events.
   - Explicitly self-limiting: "Observable sandbox execution telemetry only; no private reasoning or unsupported session fields are inferred" — no-ops cleanly on hosts without Codex logs rather than fabricating data. This is good discipline, consistent with this skill's non-negotiables.
   - Nothing consumes these events yet — no classification layer, no session reconstruction, no cost/time estimation, no lineage graph exists for this data. It's raw evidence sitting unused past ingestion.
   - Governed by its own sibling spec, `.codex/contribution-intelligence/MASTER_BUILD_PROMPT.md` — a Codex-phrased rewrite of the same overall assignment Betsy gave this skill (same "Contribution Event," same non-equate-prompt-count-with-contribution core principle), structured as 24 sections (Phase 0 Repo Inspection, Phase 1 Domain Creation, Raw Source Event Requirements, Normalization, Session Processing Pipeline, Contribution Event Detection, Lineage Engine, Contributor Identity, Time Intelligence, Cost Ledger, Traditional Build Comparator, Human Differentiation, Automatic Session Processing, **Codex Self-Instrumentation** [the only section actually built], Shared Contribution Channel, Agent Policy Model, Sales/Marketing/BU extensions, Reporting API, First User Experience, Testing, First Vertical Slice Definition of Done). Architecturally consistent with `reference/master-build-prompt.md`, not a conflicting spec — just Codex's own copy, further along on one narrow slice (raw ingestion) and behind on everything else (no domain schema, no engines, no reporting exist on the Codex side either).

3. **No Claude-side raw event adapter exists that mirrors #2's pattern.** `scripts/analyze-contribution-sessions.mjs` computes aggregates directly (console output + a gitignored summary JSON) rather than emitting immutable per-event records with stable ids — it is not idempotent-appendable the way the Codex adapter is, and nothing about it is wired into an automatic build/session hook (§VI's Session Intelligence Agent doesn't exist for Claude yet).

**As of this inspection, no contribution_events, raw_events, or lineage-graph table/schema existed anywhere in this repo** — confirmed via `CREATE TABLE` grep across `server/db.js`. Building the foundational Contribution Event schema from scratch without reconciling against the three pieces of prior art above would have created a fourth parallel model — hence pausing here for Betsy's direction rather than proceeding. See "Decisions Betsy answered" and "Phase 1 structural build" below for what was actually built once that direction came back.

## Decisions Betsy answered (2026-07-13)

1. **Storage model: Postgres tables for both**, not the Codex adapter's flat-JSON pattern. Built `raw_events` + `contribution_events` in `server/db.js`; the existing Codex JSON checkpoint (`.codex/contribution-intelligence/codex-observable-events.json`) is synced into `raw_events` via a new one-way import script rather than rewriting the already-shipped, build-pipeline-wired Codex adapter itself.
2. **Relationship to the legacy v0.17 system: the new model becomes the eventual source.** `backlog_items.hours_claude`/`cost_usd_claude`/`traditional_cost_usd` keep their current columns and keep serving `/output/methodology` unchanged for now — nothing breaks. Once Phases 4–5 land, those aggregate numbers should be recomputed as a rollup **over** Contribution Events rather than computed directly on `backlog_items`. No migration of existing backlog data into `contribution_events` has been done yet — that's Phase 4/5 work once the classifier (Phase 2) and session reconstruction (Phase 4) exist to produce something meaningful to roll up.
3. **`aiSavingsUsd`/`aiSavingsMultiple` framing: fixed now**, but scoped narrower than originally described — see "Phase 1 structural build" below for what was actually in-blast-radius vs. deliberately left alone.

## Deferred decisions (not asked this pass — proceeded with a stated default; revisit before Phase 5 / Phase 7 build)

4. **Human cost rate basis default.** Not re-asked — kept the legacy system's existing single-rate-per-contributor-type model ($225/hr Betsy across all contribution types, $115/hr Claude quality-adjusted) as the working default per decision #2 above (the new model reads from/rolls up this same rate basis for now). Revisit explicitly before Phase 5 (Cost Ledger & Traditional Build Comparator) builds out the multi-rate-basis view §VIII calls for — don't assume this single-rate model is the final answer.
5. **Centralization boundary for §XIV.** Not re-asked. The Claude-side adapter built this pass (`scripts/run-claude-contribution-intelligence.mjs`) follows the Codex adapter's existing precedent and centralizes a text snippet into `raw_events.observable_evidence` (plus the full parsed line into `raw_payload` JSONB) rather than leaving content in its native source. This is a real design choice with privacy/governance implications for Phase 7's multi-agent security model — revisit explicitly before Phase 7 (Multi-Human/Multi-Agent Channels & Agent Security), don't treat this pass's default as final.

## Phase 1 structural build (2026-07-13)

- **Schema** (`server/db.js`, additive, appended after the v0.17 block): `raw_events` (immutable; `id` = source adapter's own deterministic SHA-256 hash, so every adapter insert is naturally idempotent via `ON CONFLICT (id) DO NOTHING` — no separate dedup bookkeeping) and `contribution_events` (the versioned classification layer per §I's full field list, using JSONB for grouped fields like `scores`/`evidence_references`/`assumptions` rather than ~40 individual columns; versioned per §XX — reclassification inserts a new row sharing `contribution_event_id` with `attribution_version` incremented rather than overwriting). `contribution_events` exists but is **empty** — populating it is Phase 2's classifier, not Phase 1's job.
- **Claude-side raw event adapter** (`scripts/run-claude-contribution-intelligence.mjs`, new, mirrors the existing Codex adapter's shape): reads real `.jsonl` session transcripts from `~/.claude/projects/C--Users-mbets-saltbasin-website/`, emits one raw event per transcript line with a deterministic id, batch-inserts into `raw_events`. Wired as `npm run contribution:claude`. **Run against real data this pass**: 51 session files → 35,918 raw events inserted.
- **Codex JSON → Postgres sync** (`scripts/import-codex-raw-events.mjs`, new): one-way, idempotent import of the existing Codex adapter's JSON checkpoint into `raw_events`, leaving the Codex adapter itself untouched. Wired as `npm run contribution:import-codex`. **Run against real data this pass**: 3,086 events imported.
- **Total real evidence now in `raw_events`**: 39,004 rows (35,918 `CLAUDE` + 3,086 `CODEX`). `event_type` breakdown: 16,548 `ASSISTANT_TURN`, 9,396 `TOOL_RESULT_ECHO`, 9,069 `OTHER` (Claude Code transcript line types not yet classified more specifically — e.g. `type:"summary"` compaction lines; disclosed as `OTHER` rather than mis-classified, per the "don't fabricate" rule — Phase 2 should refine this), 3,075 `TOOL_ACTIVITY`, 576 `USER_TURN`, 329 `SYSTEM_EVENT`, 8 `FILE_UPDATE`, 3 `COMMAND_EXECUTION`.
- **Savings-language fix — scope note.** What actually got relabeled: `server/routes/methodologyStats.js`'s `/summary` route (`aiSavingsUsd`→`estimatedCostAvoidedUsd`, `aiSavingsMultiple`→`costLeverageRatio`, matching §X's own approved vocabulary) and the `/output/methodology` page it feeds (`src/components/Output.jsx`: chip labels, chart title/dataKey, "The Cost Savings Multiple" card → "The Cost Leverage Ratio", tooltip copy). **What was deliberately NOT touched**, because it turned out to be a much bigger blast radius than "one route + its consuming page": the same `aiSavingsUsd`/`aiSavingsMultiple` naming is also baked into `server/routes/backlog.js` (admin backlog totals), `server/lib/snapshot.js` (build-progress snapshot capture), and — critically — the **`build_progress_snapshots.ai_savings_usd` Postgres column itself** (`server/db.js` ~1544), plus historical rows in that table and `CHANGELOG.md` references. Renaming that would mean an actual column migration + backfill + updating every reader, which is a materially different and riskier change than what was described when this was approved. Flagging this as a real follow-up rather than silently leaving the two surfaces inconsistent or silently doing the bigger migration unapproved.
- **Verification**: ran both ingestion scripts against the live configured `DATABASE_URL` (additive-only, `ON CONFLICT DO NOTHING`, no existing rows touched) and confirmed row counts via a direct query — see numbers above. Did not run the app in a browser this pass since Phase 1 has no new UI surface (the methodology-page relabeling is copy/data-key changes to an existing page, not new UI) — recommend a quick visual check of `/output/methodology` next session to confirm the renamed chips/labels render correctly.
